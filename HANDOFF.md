# Dungeon Rule Editor: Development Handoff

Read this document when continuing development in a new Codex conversation or on another computer. It explains the product intent and decisions made with the user. [README.md](README.md) explains how to run and use the editor, [ALGORITHM.md](ALGORITHM.md) defines generation behavior, and [schema/runtime-v5.schema.json](schema/runtime-v5.schema.json) defines the shape of exported runtime JSON. **The user's latest instructions take precedence over this handoff.** Discuss unclear rule semantics and interaction details with the user before changing them.

## Purpose and scope

Build a small, visual, browser-based editor for a personal game's random dungeon **map rules**. The editor defines module types, concrete modules, connectors, directed generation relationships, quotas, and a reproducible 3D layout preview. It exports JSON for a future Unity generator. The editor does not instantiate a Unity scene, run the Unity generator, or perform final in-game collision checks.

The product deliberately focuses on maps. Item and enemy configuration, preview markers, and export fields were removed in v4. Do not restore them based on older discussions. UI copy is English; user-provided IDs are preserved. The current visual language is a dark blue-black game menu with type colors distinguishing graph nodes and preview boxes.

The implementation uses React, TypeScript, Vite, React Flow for the two-dimensional type relationship graph, and Three.js for the module and map canvases. FBX is parsed locally in the browser for bounds; the editor never renders the FBX mesh or uploads it to a server.

## Confirmed map model

- **Coordinates and assets:** X/Z are horizontal, Y points up. The UI displays metres; runtime JSON stores integer millimetres. FBX `UnitScaleFactor` converts source coordinates to metres. Each module stores an X/Y/Z axis-aligned occupancy box relative to the FBX model origin. All six bounds can be adjusted in the collapsed Advanced section. Unity is expected to use a corresponding Prefab with root and scene Transform scale 1.
- **Types and modules:** A type has an ID, display color, non-start map share, and required minimum. Type color is editor-only and is omitted from runtime JSON. A concrete module has a unique ID, type ID, bounds, and connectors. For FBX imports, the module ID comes from the filename; there is no separate required display name. Modules imported from runtime JSON remain editable even without their original FBX. The same concrete module may be selected more than once in a map. Stairs, corridors, rooms, and connectors are ordinary modules; there is no fixed floor height or floor index.
- **Connectors (ports) and door types:** A port has a unique ID within its module, local X/Y/Z center, a vertical side (`N/E/S/W`), a **door type**, and optional allowed target type IDs. Door types (`doorTypes`: ID, width, height) replace the old project-wide connector size; each size is one door type (sizes differ by more than 20 mm), and two ports join only when their door types are the same. A new project has no door types. A port's centre must lie on a vertical side face of the occupancy box (on the plane and within its extent); the opening rectangle may overhang the face's edges, top or bottom, because joining only matches centres, sides and door types. `allowedTypeIds: null` adds no restriction beyond the type relationship; a restricted port must accept the other module's type at **both** ends of a join.
- **FBX auto-setup (confirmed naming rules):** module ID = file name; type = file name before the first `_` (created automatically); the mesh named like the file is the body; every mesh whose name contains `Door` is a port with its **full mesh name** as port ID, its side from the face its centre lies on (the Unity door's local Z points outward, Y up), and its size matched to a door type within 20 mm or a new one named from its size in centimetres (`Door_400x400`). Names are never altered: invalid or duplicate names, and doors not on a side face, are errors that block that file. Original names are read from the FBX itself (`fbxModelNames`), because three's FBXLoader sanitises names. Replacing a module's model rebuilds its ports from the new file.
- **Open-top modules:** a module has `reservedAbove` (0 = Normal, millimetres = custom, null = open to sky). The generator treats that space as occupied for overlap; side faces extend up through it so door centres may sit above the body top (e.g. `Rooftop.fbx`: 1.5 m slab, door centre at 2.1 m). Import pre-ticks Open to sky when a door mesh centre is above the body top; the box itself stays the real mesh.
- **Placement preferences:** each type has `preferFar` and `preferHigh` (percent, −100 to 100, 0 = off). They multiply candidate weights by 4× per step from the start / per 3 m of floor height at 100 %, normalised per type at each search step, so they shift where a type lands without blocking placements or changing quotas. They are general tendencies (e.g. a rooftop type set to prefer high), not guarantees.
- **Directed relationships:** `A → B` permits the generator to extend from an already placed A to a new B. It does not restrict the player's travel direction through a door. The reverse relationship must be created separately. Each arrow has its own positive **relative weight**, which influences the order of legal candidates rather than setting a fixed probability or quota. A relationship to the start type is invalid.
- **Start and quotas:** The start is a special type containing one or more concrete modules. Exactly one is sampled uniformly and placed at world `(0,0,0)`. `Modules after start` excludes it. Non-start type shares must total 100%; the largest-remainder method converts shares to integer targets. `Required minimum` is included in each type's target, not added to it.
- **Assembly:** Extend from any unused connector of any placed module, so branches are possible. A new module attaches to one parent; the first version does not deliberately create cycles. Modules rotate only by multiples of 90° about Y. Both connector centers must coincide in X/Y/Z, and their rotated side normals must oppose each other. Reject positive-volume overlap between 3D occupancy boxes; touching faces, edges, or points is allowed. A fixed seed reproduces the search result. If no complete map is found, show the best partial layout and its quota warnings.
- **Preview:** Draw colored 3D occupancy boxes, not FBX meshes. One solid, empty rectangle represents each connected connector pair. An unused connector has a solid, hatched rectangle and is normal, without a warning. Unity is responsible for constructing real doors and sealing unused openings. The module canvas and map preview support orbit, pan and wheel zoom without inertia, hover highlighting, double-click focus, F to focus the hovered item, and Fit. Rotate/pan/zoom speeds are per-browser `localStorage` settings (`src/cameraSettings.ts`). Camera changes do not affect exported rules.

## Current workflow and source map

The single main workspace shows, in order, the rule network (type graph and map composition), **Models**, the 3D map preview and generation controls. Type graph nodes contain concrete module slots. Graph context menus create types and directed relationships. All details open in one docked **inspector panel** on the right (`editor.panel`, one type, module or new-type view at a time) while the graph stays interactive. The module panel imports or replaces FBX (from disk or from Models), edits advanced bounds, places and drags connectors on the 3D box, and edits a port's ID, coordinates and target types inline or in the popup shown when the port is clicked. **Models** holds unassigned FBX files uploaded as a folder or a batch; each has an editable module ID (`editor.libraryIds`) and becomes a module when assigned to a type. File actions live in the top-left menu. IDs are always displayed exactly as typed; no CSS case transforms are used.

Runtime JSON and editable project ZIP are both **v5**. There is no migration from v4 or older files or old browser drafts: older imports report an unsupported version. `src/model.ts` defines data, defaults, validation, runtime export, and `normalizeEditor` (which also opens editor state saved before the inspector panel, when it held floating `windows`); `src/generator.ts` implements layout search; `src/geometry.ts` handles port placement and `portsFromDoorMarkers`; `src/io.ts` handles FBX analysis (`analyzeFbx`) and ZIP/JSON; `src/importer.ts` applies FBX imports (modules, ports, door types, auto-created types); `src/autosave.ts` manages the local draft; `src/App.tsx`, `src/WorkspaceWidgets.tsx` and `src/ThreeCanvas.tsx` implement the main UI; `src/theme.css`, loaded last, holds the type scale and the inspector, Models and camera styles. Regression tests are in `tests/core.test.ts`.

The editable project autosaves in the **current browser's IndexedDB**; unassigned Models files are stored beside module FBX files under `library:<file name>` keys. Save ZIP includes rules, editor layout, original FBX files (`assets/<moduleId>.fbx`) and unassigned Models files (`library/<n>.fbx`, listed in the optional `library` field of `project.json`, omitted when empty). Export JSON includes runtime map rules, occupancy boxes, and connectors, but no FBX or editor layout. The repository contains neither user map drafts nor the Unity project or private FBX assets. The repository's `schema/runtime-v4.schema.json` is a specification for runtime JSON, **not** a particular exported map.

Use Node.js 24 and run `npm ci`, `npm test`, and `npm run build`. The GitHub Actions workflow tests, builds, and deploys `main` to [GitHub Pages](https://xuyuli1.github.io/dungeon-rule-editor/). The last functional v4 commit was `88fc1ae`; its 13 tests, production build, and Pages deployment passed at the time. Recheck the current branch rather than assuming that historical result still applies. A real `StairsRoom.fbx` from the user's Unity project parsed to model-relative Y bounds of 0–15 metres. This checked FBX conversion, **not** Unity runtime generation.

## Continuing on Windows

1. Clone `https://github.com/xuyuli1/dungeon-rule-editor.git` and open that checkout as the Codex workspace. In a new chat, say: “Read `HANDOFF.md`, `README.md`, `ALGORITHM.md`, and `schema/runtime-v5.schema.json`. Summarize the product goal and data boundaries. Check repository status, tests, and build before editing. Wait for my next feature request.”
2. Cloning the repository does **not** transfer a map saved in the Mac browser. To continue editing the same map, use **Save ZIP** on the original browser, transfer that ZIP to Windows, and use **Open ZIP** there. Runtime JSON alone cannot restore the original FBX files or editing layout.
3. Transfer a real FBX separately if a new change needs testing against the user's assets. Public source control contains sample rules and automated tests without private models.

Keep editor and Unity interpretations of units, origin offsets, rotations, connector permissions, and weight semantics aligned. When changing runtime rules, update the schema, algorithm document, import/export behavior, and meaningful tests together. Do not commit a user's ZIP, FBX, Unity project, or private exported rules to the public repository.
